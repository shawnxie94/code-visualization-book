# 内容定位说明

本文档用于固定《Code Visualization》新版书稿的读者、边界、核心观点和写作取舍。后续章节扩写、资料补强、图片规划和样章打磨都应以本文档为基础。

## 一句话定位

这本书讨论 AI 时代的代码可视化与代码理解：如何把源码、程序分析、运行时观测、变更历史和组织信息转化为可查询、可验证的软件事实，并进一步服务人类开发者、Reviewer 和 AI Agent。

## 核心观点

AI 让代码生成和修改变得更快，但没有让代码理解、影响面判断和变更验证自动消失。相反，当 AI Agent 能跨文件、跨模块甚至跨仓库修改代码时，软件团队更需要一套结构化的软件理解系统。

本书的核心观点是：

> AI 时代的代码可视化不应停留在“把代码画出来”，而应升级为软件理解基础设施。它既帮助人理解复杂系统，也为 AI Agent 提供上下文、边界、证据和验证能力。

## 目标读者

已确认的目标读者优先级：

1. AI Coding / AI Agent 工具建设者。
2. 架构师、技术负责人、研发效能负责人。
3. 有中大型项目经验、希望系统理解代码关系和变更影响的高级开发者。

优先读者：

1. 正在使用或建设 AI Coding / AI Agent 工具的人，希望理解 Agent 为什么需要结构化上下文和验证证据。
2. 架构师、技术负责人、研发效能负责人，希望把代码理解能力沉淀为工程基础设施。
3. 有中大型项目经验的开发者，希望系统理解代码关系、影响面和架构边界。

次要读者：

1. 对程序分析、代码图谱、工程可视化感兴趣的开发者。
2. 希望从传统代码可视化过渡到 AI 时代软件理解系统的工具开发者。

暂不优先服务的读者：

1. 只想学习编译器完整实现的人。
2. 只想寻找某个具体工具推荐清单的人。
3. 只想学习某种图数据库或前端可视化库使用方法的人。

## 读者读完后应该获得的能力

读者应能获得四类能力：

1. 原理理解：知道 AST、符号表、CFG、DFG、调用图、Trace、Coverage、变更历史等事实从哪里来。
2. 图谱建模：能够把代码结构、运行时行为、变更历史和组织信息抽象成节点、边和属性。
3. 工程判断：能够用代码图谱和可视化证据支持代码库理解、变更影响分析、架构理解与遗留系统改造。
4. AI 应用：能够设计 Agent 上下文包、图谱查询接口、AI Review 证据层和 AI 修改后的验证报告。

## 本书讲什么

本书重点讲五件事：

1. 代码数据如何被结构化：从源码文本到 AST、符号、类型、IR、CFG 和 DFG。
2. 程序事实如何被融合：静态分析、动态分析、变更分析和组织数据如何进入统一事实层。
3. 代码图谱如何建模：节点、边、属性、证据来源、存储选择和查询能力。
4. 核心工程场景如何落地：代码库理解、变更影响分析、架构理解与遗留系统改造。
5. AI 时代如何使用这些能力：Agent 上下文工程、代码图谱查询、AI Review 证据、AI 辅助重构和软件理解基础设施。

## 本书不讲什么

为了避免全书重新变成传统案例合集，以下内容不单独展开成主线：

1. 不做代码可视化工具测评合集。
2. 不深入讲完整编译器实现、优化器实现或虚拟机实现。
3. 不单独展开性能分析、安全分析、质量检测、精准测试等所有工程场景。
4. 不把重点放在某一个图数据库、前端图形库或商业工具的使用教程上。
5. 不把 AI 写作本身作为主题，本书讨论的是 AI 时代的软件理解与工程验证。

这些内容仍会作为子能力出现：

| 内容 | 放置位置 |
| --- | --- |
| 性能分析 | 动态分析、运行时证据、AI Review 证据 |
| 安全分析 | DFG、数据流、Review 证据、验证报告 |
| 精准测试 | 变更影响分析、相关测试查询 |
| 代码质量 | 静态分析、架构理解、遗留系统改造 |
| 工具实践 | 章节参考资料、实践项目、资料卡 |

## 写作深度

本书采用“技术科普 + 工程方法论 + 工具建设手册”三者结合的风格：先把概念讲清楚，再说明工程判断方法，最后给出可以复现的最小系统设计。

写作深度是“能解释原理，能指导工程设计，但不陷入实现细节泥潭”。

写作时应遵循：

1. 原理章节要有最小代码例子和可视化解释。
2. 图谱章节要给出实体、关系、属性和查询示例。
3. 工程场景章节要说明输入、分析过程、输出报告和工程流程位置。
4. AI 应用章节要说明 Agent 为什么需要该能力，以及如何形成可审计证据。
5. 实践章节要给出数据结构、接口设计和输出样例。

## 实践项目取舍

实践项目采用“适合讲解和复现优先”的技术取舍，不追求一次性覆盖最完整的工业实现。

已确认原则：

1. 可以出现多种语言和技术栈选择，但正文应优先选择最容易讲清楚、最容易复现的方案。
2. 示例语言可以根据章节目标选择，不强制全书只使用一种语言。
3. 实践项目要把重点放在数据流、图谱模型、查询接口和验证报告，而不是堆叠复杂框架。
4. 如果存在多种实现路线，正文应说明推荐路线和替代路线的取舍。

当前默认倾向：

| 模块 | 默认取舍 |
| --- | --- |
| 源码解析 | 以容易解释的 AST 工具为主，可对比 JavaParser、Tree-sitter、TypeScript Compiler API |
| 图数据存储 | 先用 JSON 或 SQLite 讲清楚模型，再说明 Neo4j 等图数据库适合扩展场景 |
| 可视化 | 先用 Mermaid 和简单页面表达核心关系，再考虑更复杂的图可视化库 |
| Agent 接口 | 优先采用 MCP 风格或工具调用风格说明，强调协议思想和 JSON 输入输出 |
| 案例数据 | 使用模拟仓库、模拟 PR、模拟 Agent 修改，不引入真实项目案例 |

## 案例策略

本书不加入真实案例，采用模拟案例说明。

模拟案例应满足：

1. 足够小，读者能在一章内理解上下文。
2. 足够真实，能体现跨文件调用、测试关联、变更影响和 Agent 上下文缺失等问题。
3. 可以贯穿多个章节复用，例如同一个示例仓库从 AST 解析、图谱构建、影响面分析一直用到 Agent 查询接口。
4. 避免使用真实公司、真实业务和真实代码，以降低隐私、版权和解释成本。

## 发布与视觉风格

已确认发布形式：

3. PDF、公众号连载可以作为后续衍生形式，不作为当前主线。

已确认图片风格：

- 技术书籍风。

视觉取舍：

1. 优先使用清晰、克制、信息密度适中的技术图。
2. Mermaid 适合流程草图和关系草图。
3. 关键技术图后续可转成 SVG 或 PNG。
4. AI 生图只用于封面、章节头图或概念插画，不替代需要精确表达的技术图。

1. 是否服务“AI 时代软件理解系统”这个主线。
