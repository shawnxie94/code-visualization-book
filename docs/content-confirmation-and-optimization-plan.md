# 内容确认与优化推进方案

本文档记录内容确认、样章定标和批量优化阶段的推进方式。目录已经与 `SUMMARY.md` 对齐，HonKit 与 Mermaid 预览链路可用。下一步重点不是直接批量扩写，而是先确认内容标准，再用样章建立可复用的写作模板。

公开正文应按正常技术书籍组织，不在前言或章节中描述写作过程、旧稿处理或目录迁移历史。完成标准见 [`definition-of-done.md`](definition-of-done.md)（已升级为**出版级终稿 RC**，旧“可读闭环”只算 Beta）。

## 当前状态判断

当前书稿已具备：

1. 目录与 `SUMMARY.md` 对齐，主线为“原理 -> 图谱 -> 核心工程场景 -> AI 时代应用 -> 实践项目”。
2. 章节骨架齐全，并统一使用 `mini-shop` 作为贯穿模拟案例。
3. 关键章节已补充 Mermaid 图示、参考链接和后续 AI 配图备注。

当前主要风险不是目录不清楚，而是后续扩写时可能出现三个问题：

1. 章节深度不一致：有的章节偏概念，有的章节偏工具，有的章节偏工程经验。
2. AI 时代主线被削弱：如果传统场景继续展开过多，全书会重新变成案例合集。
3. 证据来源不足：一些判断需要来自官方文档、论文、工程实践或可复现实验，而不是只靠经验描述。

## 提案选择

### 方案 A：直接逐章扩写

做法：按照 `SUMMARY.md` 从第一章开始逐章扩写。

优点：

- 推进速度快。
- 每次任务边界清楚。

缺点：

- 容易越写越散。
- 不同章节的结构和深度可能不一致。
- 后期统一风格和术语的返工成本较高。

适用情况：目录和写作标准都已经完全确定时再使用。

### 方案 B：章节质量矩阵 + 三个样章定标

做法：先为 28 个章节建立质量矩阵，再选择 3 个代表性样章打磨到较高完成度，最后按样章标准批量扩写其他章节。

推荐选择该方案。

优点：

- 能先统一章节目标、深度、图示、案例和引用要求。
- 能控制传统工程场景篇幅，避免偏离 AI 时代主线。
- 适合后续配合 AI 写作批量生成和修订。

缺点：

- 前期会多花一点规划时间。
- 需要先接受“不是马上扩写全部章节”的节奏。

适用情况：当前书稿已经有目录和初稿，但需要确认质量标准和写作边界。

### 方案 C：资料研究优先

做法：先围绕每章收集大量资料、论文、工具文档和案例，再开始扩写。

优点：

- 事实基础更扎实。
- 适合技术深度较强的章节。

缺点：

- 容易陷入资料收集，迟迟不进入正文打磨。
- 对当前这本书来说，部分章节并不需要过重的研究投入。

适用情况：用于补强重点章节，不适合作为全书第一步。

## 最终选择

采用方案 B：章节质量矩阵 + 三个样章定标。

原因：

1. 当前目录已经稳定，但章节内容还处在初稿阶段，最需要统一质量标准。
2. 本书不是工具手册，也不是论文综述，必须在“原理解释、工程场景、AI 应用”之间保持平衡。
3. 后续希望借助 AI 写作完成全书，越早建立章节模板、术语规范和证据要求，后续生成质量越稳定。

方案 C 作为辅助策略：只对重点章节做资料补强，不作为全书推进的主线。

方案 A 暂缓：等样章标准确定后，再进入批量扩写。

## 推进步骤

### 阶段 1：确认全书定位

目标：把这本书的读者、边界和核心观点写清楚。

建议新增或补充一份定位说明，回答以下问题：

1. 目标读者是谁：高级开发、架构师、技术负责人、AI Coding 工具建设者，还是希望理解 AI Agent 工程化的研发人员。
2. 读者读完后应该获得什么能力：理解代码可视化原理、搭建最小代码理解系统、设计 Agent 上下文和 Review 证据层。
3. 本书不讲什么：不做工具测评合集，不深入编译器实现细节，不铺开所有工程应用场景。
4. 本书核心观点是什么：AI 时代代码理解会从个人经验升级为软件工程基础设施。

产物：

- `docs/content-positioning.md`
- 或者把定位说明整合进 `README.md`

完成标准：

- 能用一页内容说明本书写给谁、解决什么问题、不解决什么问题。

### 阶段 2：建立章节质量矩阵

目标：给 28 个章节建立统一检查表，避免后续扩写失控。

建议字段：

| 字段 | 说明 |
| --- | --- |
| 章节 | 对应 `SUMMARY.md` 中的章节 |
| 章节类型 | 原理 / 图谱 / 工程场景 / AI 应用 / 实践 |
| 核心问题 | 本章要回答的一个关键问题 |
| 必讲概念 | 本章必须讲清楚的概念 |
| 示例要求 | 是否需要代码例子、系统例子或 PR 例子 |
| 图示要求 | Mermaid、静态图、AI 配图或无需图 |
| 参考资料 | 官方文档、论文、工程案例或产品文档 |
| 当前状态 | 草稿 / 可读 / 需扩写 / 需重写 |
| 下一步动作 | 资料补强、结构调整、样章打磨或正文扩写 |

产物：

- `docs/chapter-quality-matrix.md`

完成标准：

- 28 个章节都有明确目标、内容深度、图示要求和下一步动作。

### 阶段 3：选择并打磨三个样章

目标：用三个章节分别定义三类章节的写作标准。

推荐样章：

1. `part2/source-to-ast.md`
   - 类型：原理讲解型章节
   - 目标：定义“概念解释 + 最小代码例子 + 可视化表达 + AI 时代意义”的写法。
2. `part4/change-impact-verification.md`
   - 类型：工程场景型章节
   - 目标：定义“问题场景 + 分析方法 + 报告结构 + 工程流程接入”的写法。
3. `part5/agent-context-engineering.md`
   - 类型：AI 时代应用型章节
   - 目标：定义“AI 风险 + 上下文工程 + 图谱查询 + 审计证据”的写法。

每个样章建议统一包含：

```text
本章要解决的问题
核心概念
一个最小例子
可视化或图谱视角
工程中的用法
AI 时代的新意义
常见误区
小结
延伸阅读
```

产物：

- 三个完成度较高的样章
- 一个可复用的章节写作模板

完成标准：

- 三个样章的结构、语气、深度和引用方式基本一致。
- 后续章节可以按样章模式扩写，而不是重新设计结构。

### 阶段 4：补强资料与引用体系

目标：为重点章节建立可靠资料来源。

资料类型：

1. 官方文档：Tree-sitter、ANTLR、LLVM、OpenTelemetry、CodeQL、GitHub Copilot、VS Code Copilot。
2. 研究资料：SWE-bench、RAG for code、repository-level code generation、program analysis。
3. 工程案例：测试选择、影响面分析、服务目录、架构治理、代码图谱。
4. AI Agent 实践：上下文工程、工具调用、代码 Review 证据、变更验证。

推进方式：

- 每个重点章节至少准备 2 到 5 个可靠来源。
- 正文不必堆砌引用，但关键判断要能追溯。
- 资料先进入章节 brief，再进入正文。

产物：

- 每章资料卡
- 或在 `docs/ai-writing-framework.md` 的资料卡流程下维护

完成标准：

- 样章中的关键判断都有来源支撑。
- 参考链接不是只放在文末，而是能反向支撑章节观点。

### 阶段 5：统一图示与图片策略

目标：形成全书统一的视觉表达方式。

建议分三层处理：

1. Mermaid 图：流程图、架构图、数据流、查询链路。
2. 手工或导出图：AST、CFG、DFG、代码图谱模型等需要准确表达的技术图。
3. AI 生图：封面、章节头图、概念插画、PR Review mockup。

当前策略：

- Mermaid 图先作为可渲染草图保留。
- AI 配图备注先保留在章节中，等正文稳定后统一生成。
- 技术解释图优先考虑 SVG 或 PNG，避免只依赖 AI 生图。

产物：

- `docs/image-plan.md`

完成标准：

- 每个需要图片的章节都有明确图示类型、用途和生成方式。

### 阶段 6：批量扩写与一致性审校

目标：在样章定标后，按同一标准扩写其他章节。

建议顺序：

1. 先补齐第二篇和第三篇，确保原理基础扎实。
2. 再打磨第四篇，控制传统工程场景只保留核心 3 个。
3. 然后强化第五篇，突出 AI 时代新应用。
4. 最后完善第六篇，让实践项目能跑通“采集 -> 建图 -> 分析 -> 可视化 -> Agent 查询 -> 验证报告”闭环。

一致性检查项：

- 术语是否一致：代码图谱、软件理解系统、Agent 上下文、证据层。
- 篇章递进是否顺畅：原理 -> 图谱 -> 工程场景 -> AI 应用 -> 实践。
- 第四篇和第五篇是否重复。
- 实践篇是否有足够的数据结构、接口和输出示例。
- Mermaid 图、参考链接、AI 配图备注是否风格一致。

完成标准：

- 每章都有明确问题、核心内容、图示或例子、小结和参考资料。
- 全书主线没有回退成传统应用场景合集。

1. 补齐成书资产：`docs/glossary.md`、`docs/image-plan.md`、`docs/research-cards/`、审校清单。

3. 按样章标准把其余 25 章从“可读”提升到“定稿”，并按丰富度标准加厚（例子/模板/失败模式/练习）。
